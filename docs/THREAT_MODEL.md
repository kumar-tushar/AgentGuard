# AgentGuard threat model

## 1. Overview

AgentGuard is one local Chrome MV3 extension for individual and managed users. It observes accessible HTTP(S) tabs automatically, combines explainable automation signals, evaluates separate hostname policies, and can replace/close a selected tab or request optional tab-scoped network containment. It is not an authenticated AI-agent inventory or an endpoint security boundary. User requirements prohibit collecting page content, credentials, cookies, form values and full URLs. This source-backed model describes the implemented automatic-monitoring/session milestone, not all planned capabilities or a completed vulnerability audit.

## 2. Threat Model, Trust Boundaries, and Assumptions

Protected assets are telemetry privacy, assessment/document association, honest uncertainty, managed-policy integrity, and scoped extension authority. Hostnames remain sensitive even without page contents. Downloaded reports leave extension retention controls. Local storage is not tamper-evident against a profile writer, compromised extension, browser or OS.

A hostile page controls MAIN-world globals, script-dispatched events and navigation timing. It can spoof fingerprints or hide WebDriver; it does not initially control Chrome's sender/document metadata, trusted-context storage or packaged UI. MAIN snapshots are rebuilt from an allowlist. Isolated sensor messages require the same extension, active top-frame HTTP(S) document, exact bounded fields, freshness and sequence/rate validation; the worker rechecks Chrome's current document before scheduling. The sensor channel cannot issue privileged commands. (`src/detection/validation.ts:24`, `src/background/sensor-messages.ts:15`, `src/background/worker.ts:307`.)

Popup, options and blocked pages share command authority. Their origin/path guard is the worker boundary; UI confirmations are not separate worker-authenticated gesture tokens. No external message entry point or remote upload implementation exists. Managed values are enforced in worker save logic, not merely by disabled UI controls. Configuration failure is visible degradation, not guaranteed fail-closed network isolation. (`src/background/messages.ts:4`, `src/background/settings.ts:5`, `src/background/worker.ts:139`.)

An external controller may use CDP/WebDriver/accessibility/OS input, generate trusted events, conceal signals, navigate away or open new tabs. Generic signals do not identify its vendor. Required debugger permission confers more authority than the implementation's passive use; distribution integrity matters. Extension isolation, browser policy enforcement and sender metadata are Chrome trust assumptions. Ordinary authorized settings changes, exports and removal by a permitted local user are not privilege escalation.

Current coverage overrides historical session state. UNMONITORED does not mean automation ended and must not renew old evidence. Activity counters are currently not supplied to session observations; zero means integration unavailable, not inactivity. Strong ACTIVE/CONNECTED correlation, cross-tab alerts, delegation, attestation and enterprise transport remain pending. The automatic permission/state documentation was corrected during this milestone; former activeTab/HUMAN descriptions were stale, not accepted controls. Real managed Chrome, native consent, evasion and false-positive rates remain deployment checks. (`src/background/worker.ts:68`, `src/background/worker.ts:230`, `src/background/session-observation.ts:109`, `src/shared/intelligence.ts:2`.)

Durable recovery snapshots are bounded and disabled with zero history retention. At full restart, prior tab IDs do not regain live authority. If a history write fails and a full restart then destroys the session-area journal, only the last successful durable state can be recovered; this is a documented non-transactional storage limitation, not a successful clear/end guarantee. (`src/background/agent-sessions.ts:228`, `src/background/agent-sessions.ts:264`.)

## 4. Severity Calibration (Critical, High, Medium, Low)

- Critical: only with evidence of broadly reachable, high-impact browser/organization compromise and a real additional capability. No backend/tenant system exists here; do not invent organization-wide reach from one local tab.
- High: a visited page crossing the trusted message/storage boundary to extract retained telemetry or invoke broad privileged operations. A malicious installed update has serious impact but requires a distinct supply-chain prerequisite.
- Medium: reachable document-association bugs causing wrong-tab containment, material managed-policy bypass, or persistent attacker-driven resource exhaustion. Ordinary detector spoofability alone is not proof of a new privilege boundary crossing.
- Low: narrowly scoped misleading stale information or recoverable local disruption with constrained impact. Cosmetic inaccuracies do not automatically become vulnerabilities.

Already authorized UI export/clear and actions by an OS/profile owner do not gain authority the actor lacked. Chrome's inability to identify arbitrary debugger owners is a platform limitation, not proof of a bug. Confidence in evidence is separate from impact; untested deployment assumptions remain questions. This model establishes no audit certification, exclusions or owner-approved risk acceptance.

Review basis: mutable working tree, offline source inspection plus one independent fresh-context architecture review. Source paths/anchors were checked; runtime test results are recorded separately in ACCEPTANCE.md. Model generation used only the user-requested repository output, not a shared security cache.
